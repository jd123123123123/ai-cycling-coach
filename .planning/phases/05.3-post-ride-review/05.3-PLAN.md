<objective>
When the athlete has already trained today, don't just say "nice, you're done" — **grade the ride** against what their body-state, periodization phase, and goal would have prescribed, and tell them scientifically where this session puts them on their path to race day.

This is the "mindblowingly good" feature — post-ride feedback that feels like a real coach sitting down with your data after the session.

**Four new outputs every post-ride review contains:**

1. **Compliance grade** — `perfect | strong | okay | overcooked | undercooked`
   - Perfect: duration + intensity both within ±10% of what the periodization layer would have picked
   - Strong: one metric within 10%, other within 25%
   - Okay: both within 25%
   - Overcooked: >25% above target (too much TSS or too much time-in-zone above target)
   - Undercooked: >25% below target

2. **Physiological read** — 2-3 sentence scientific interpretation:
   - Technical: "EF 1.52 (up from 1.48 trailing 4-week) signals aerobic base deepening per San Millán's Pw:HR drift framework. Variability Index 1.06 — you held target power steady."
   - Simple: "Your heart rate stayed low relative to your effort today — that's a real sign your base fitness is building. You paced it evenly, which is exactly how this kind of ride does its job."

3. **Goal trajectory update** — project forward using current CTL trajectory + weekly TSS pattern:
   - "CTL is +0.8/week. At this rate you'll hit 45 by race day (target 48). Stay above 300 TSS/week for the next 3 weeks to close that gap."
   - "TSB projected to land at +12 on race day — perfect taper window per Mujika (+5 to +25)."

4. **Next-session nudge** — specific, scientific, actionable:
   - "More of this next time" / "Tomorrow: rest is earned" / "Next hard session: VO2 — your aerobic base can handle it now" / "Dial intensity back 10% next threshold block"

Do all this for BOTH the completed-today case (primary) AND retrospectively for yesterday when the athlete opens the app the next morning.
</objective>

<context>
**What we have to work with (per-activity):**
- `Activity.tss`, `.normalized_power`, `.average_hr`, `.average_power`, `.duration_seconds`, `.distance_meters`
- `athlete.ftp` + zone definitions
- Coggan's Variability Index = NP / avgP (>1.1 = pacing was uneven)
- Efficiency Factor = NP / avgHR
- Decoupling (already computed in `advanced_metrics.compute_activity_metrics`)

**What we DON'T have (explicitly out of scope for v1):**
- Per-second power/HR streams. The activity summary is enough for v1 grading.
- Interval-by-interval detection (can we tell if a 5×4min VO2 set was done vs freelance intervals?). Future feature.

**Comparison target — the "should have been" workout:**

When the ride happened today, we still have today's picked `session_type` + picked template from the periodization layer. That's what the coach *would* have prescribed had the user opened the app first. Use that as the comparison baseline.

If we can't infer what "should have been" (e.g. very sparse CTL history, no athlete profile) we fall back to a simple per-hour TSS band + zone-distribution heuristic for the phase.

**Dependency rule:**
- Post-ride review is only attached to the brief when `today_tss >= 25` (the same threshold used by the "acknowledge completed" branch).
- When present, it REPLACES the "you're done, rest" rationale with a compliance-scored version. The `prescribed_workout` stays `rest_day` (same rule as 05.1-01 Monday fix).

**Scientific grounding (cite in the review):**
- Coggan: TSS, NP, VI, IF
- San Millán: Z2 HR drift, EF trend
- Banister: CTL/ATL/TSB projection
- Seiler: Polarized zone ratio check ("was this session polarized or grey-zone")
- Friel: Periodization-phase appropriateness ("good build-phase session")
- Kolie Moore: If we had RPE data, we'd flag RPE-power decoupling. Note as a future hook.
</context>

Create `backend/app/services/ride_compliance.py`.

```python
from dataclasses import dataclass
from typing import Literal

Grade = Literal['perfect', 'strong', 'okay', 'overcooked', 'undercooked']

@dataclass(frozen=True)
class CompliancePair:
    target: float
    actual: float
    delta_pct: float       # (actual - target) / target * 100
    band: Literal['match', 'over', 'under']  # match = within ±10%

@dataclass(frozen=True)
class RideCompliance:
    grade: Grade
    duration: CompliancePair
    tss: CompliancePair
    intensity_factor: CompliancePair | None  # IF = NP / FTP
    variability_index: float | None          # VI = NP / avgP
    ef: float | None                          # NP / avgHR
    decoupling_pct: float | None             # Pw:HR drift %
    zone_match_pct: float | None              # 0..100 — how close actual zone dist matches target
    # Phase context — used by narrative layer
    phase: str
    session_type: str
    template_id: str                          # what would have been picked

def score_ride(
    actual_activity: Activity,
    target_template: WorkoutTemplate,
    ftp: int,
    phase: str,
    session_type: str,
) -> RideCompliance:
    """Grade a single completed ride against the template that would have
    been prescribed for the same day-state.
    """
```

Grading logic:
- **Perfect:** `|duration.delta_pct| <= 10 AND |tss.delta_pct| <= 10`
- **Strong:** (one <= 10 AND other <= 25) OR (both <= 20)
- **Okay:** both <= 30 and no severe outlier
- **Overcooked:** duration > target+30% OR tss > target+30% (either crosses the "too much" line)
- **Undercooked:** duration < target-30% OR tss < target-30% (crossed "too little")
- Mixed (e.g. short + hard): prefer `overcooked` if tss is high, else `undercooked`

Pure functions. Unit tests at `backend/tests/test_ride_compliance.py` with synthetic Activity fixtures covering each grade.

<task id="2" name="goal-trajectory-service">
Create `backend/app/services/goal_trajectory.py`.

```python
@dataclass(frozen=True)
class TrajectoryProjection:
    days_to_goal: int | None
    ctl_now: float
    ctl_7d_delta: float           # change over trailing 7d
    ctl_projected_at_goal: float  # linear extrapolation
    ctl_target: float | None       # from athlete.goals.target_ctl (if set)
    tsb_projected_at_goal: float   # based on current taper pattern
    taper_window: Literal['too_flat', 'ideal', 'too_fresh', 'overreached', 'unknown']
    on_track: Literal['ahead', 'on_track', 'behind', 'no_goal']
    weekly_tss_required: float     # to close CTL gap
    weekly_tss_actual: float       # trailing 4-week average
    narrative_hook: str            # one-line "what this means" for the UI

def project(
    user_pmc: list[PMCEntry],     # last 90 days
    athlete_goals: dict | None,   # {target_ctl, event_date, weekly_hours}
    phase: str,
) -> TrajectoryProjection:
    """Linear extrapolate CTL from trailing 7d delta; compute TSS needed."""
```

Key math:
- `ctl_projected = ctl_now + (ctl_7d_delta / 7) * days_to_goal`
- `gap = target_ctl - ctl_projected` (if goals.target_ctl set)
- `weekly_tss_required = weekly_tss_actual + gap * 7` (approx, to close gap by goal date)
- `taper_window` from Mujika: ideal +5 to +25 TSB on race day, overreached < -15

Tests at `backend/tests/test_goal_trajectory.py` — boundary cases for each `taper_window` and `on_track` state, and the "no goal date set" path.
