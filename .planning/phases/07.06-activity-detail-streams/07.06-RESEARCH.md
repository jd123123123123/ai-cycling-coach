# Phase 7.06: Activity Detail with Streams — Research

**Researched:** 2026-05-05
**Domain:** Garmin stream fetch, FIT file parsing, JSONB storage, SideSheet enhancement, time-series charting
**Confidence:** HIGH (all findings from direct codebase inspection and installed library source)

---

## Summary

Phase 7.06 enhances the existing `RecentActivities` SideSheet (already open-on-row-click via Phase 06.1-02) from a simple stats grid into a full activity detail panel with headline metrics and time-series charts. The phase adds a `sample_streams` JSONB column to the `activities` hypertable, a `GET /activities/{id}/streams` endpoint, stream fetching during Garmin sync, and two to four Recharts time-series graphs inside the SideSheet.

**What exists today:** `SideSheet` primitive is fully built at `frontend/src/components/ui/SideSheet.tsx`. `RecentActivities.tsx` already wires `SideSheet` with an `ActivityDetail` component that renders a stats grid. The grid shows TSS, NP, avg HR, distance, duration, source. The SideSheet opens when a row is clicked; `selectedId` state manages open/close. No streams or charts exist yet.

**Stream source decision:** The `garmin-health-data` library (`GarminHealthDataClient`) does NOT have a typed stream-fetch method. Two paths are available: (a) call `_connectapi("/activity-service/activity/{garmin_id}")` which returns detailed summary + optional `metricDescriptors`/`activityDetailMetrics` arrays used by Garmin Connect web for its charts; (b) call `download_activity(garmin_id, ORIGINAL)` to get a zipped FIT file and decode it with `fitdecode`. Path (a) is the right choice for this phase: it is a single synchronous JSON call per activity (no unzipping/decoding), returns HR, power, cadence, altitude, speed streams already timestamped, and the library already uses `_connectapi` for non-standard endpoints (HRV, body battery, training readiness). Path (b) is more complete but requires decompressing a ZIP, reading a binary FIT, and is heavier per-activity — defer to a future phase if fidelity matters more.

**Primary recommendation:** Store streams as a nullable `JSONB` column `sample_streams` on `activities`. Fetch via `_connectapi("/activity-service/activity/{external_id}")` during sync. Downsample to ~500 points max at write time. Serve via `GET /activities/{id}/streams`. Render with uPlot (already installed) inside the existing SideSheet — same pattern as `IntradayModal.tsx`.

### Pattern 1: JSONB Streams Storage Shape

**What:** Store downsampled streams as a nullable JSONB dict on the Activity row.
**When to use:** Always; matches `raw_data` already on Activity.

```python
# Shape stored in activity.sample_streams (None if no streams available)
{
  "sampled_at": "2026-05-05T08:30:00Z",   # ISO when streams were fetched
  "source": "garmin_connectapi",
  "points": 487,                            # actual point count after downsample
  "t": [0, 2, 4, ...],                     # elapsed seconds from activity start
  "hr": [142, 143, null, 145, ...],         # bpm | null
  "power": [210, 215, null, ...],           # watts | null (cycling only)
  "elevation": [142.3, 142.5, ...],         # metres | null
  "speed": [7.2, 7.4, ...],                # m/s | null
  "cadence": [88, 89, null, ...]            # rpm or spm | null
}
```

Nulls signal sensor dropout; frontend charts use `spanGaps: false` (same as IntradayModal uPlot series config).

**Size analysis (MEDIUM confidence — derived from typical Garmin data):**
- 1-hour ride at 1Hz = 3600 data points × 5 fields = ~90 KB raw JSONB
- After downsample to 500 points: ~12 KB per activity
- 500-point target gives adequate visual resolution for a 600px-wide chart (1.2px per point)
- Garmin's own chart endpoint typically returns 100–1000 samples depending on activity length (it auto-selects resolution)

### Pattern 2: GarminProvider Protocol Extension

**What:** Add `get_activity_details` to the Protocol and GarminHealthDataClient.
**When to use:** During sync, after a new activity is inserted, if it is cycling or running.

```python
# In garmin_client.py Protocol:
async def get_activity_details(self, garmin_activity_id: str) -> dict | None: ...

# In GarminHealthDataClient:
async def get_activity_details(self, garmin_activity_id: str) -> dict | None:
    await self._ensure_auth()
    try:
        return await asyncio.to_thread(
            self._wrap,
            self._api._connectapi,
            f"/activity-service/activity/{garmin_activity_id}",
        )
    except Exception:
        return None  # streams are optional; activity sync must not fail
```

The Garmin Connect `/activity-service/activity/{id}` endpoint returns a dict with:
- `activityDetailMetrics`: list of `{metricsType, metrics: [...]}` objects where each `metrics` list is the time-series values for a sensor channel.
- `metricDescriptors`: list of `{metricsIndex, key, unit}` that maps indices to field names like `"directHeartRate"`, `"directPower"`, `"enhancedAltitude"`, `"enhancedSpeed"`, `"directBikeCadence"`.
- Sampling rate is irregular (Garmin picks resolution); always rebuild a uniform-time array during mapping.

**Confidence:** MEDIUM. The endpoint path is standard Garmin Connect API confirmed by community reverse-engineering. Exact field keys LOW confidence — need runtime validation.

### Pattern 3: Sync Extension (Opt-in, non-blocking)

**What:** After inserting a new activity in `sync_activities`, attempt to fetch streams; failure must not fail the activity record.
**When to use:** For cycling/running activities from Garmin source.

```python
# In garmin_sync_service.sync_activities(), after create_activity():
if mapped.sport in ("cycling", "running") and mapped.external_id:
    try:
        raw_detail = await client.get_activity_details(mapped.external_id)
        if raw_detail:
            streams = map_activity_streams(raw_detail, mapped.duration_seconds)
            if streams:
                # Update the activity we just created with streams
                stmt = (
                    select(Activity)
                    .where(Activity.user_id == user_id,
                           Activity.external_id == mapped.external_id)
                )
                result = await db.execute(stmt)
                act = result.scalar_one_or_none()
                if act:
                    act.sample_streams = streams
                    await db.flush()
    except Exception as exc:
        logger.warning("Stream fetch failed for %s (non-fatal): %s",
                       mapped.external_id, exc)
```

**Stream fetch adds ~1s per new cycling/running activity** (one extra HTTP call). Initial backfill of 90 days could be 50-200 activities × 1s = significant latency. Backfill streams async with a separate button or background job. Forward sync (incremental) adds negligible delay.

### Pattern 5: Headline Metrics Derivation

**What:** NP, IF, TSS, EF are needed in the SideSheet header. Check what already exists.
**Where they live today:**

| Metric | Source | Status |
|--------|--------|--------|
| TSS | `Activity.tss` ORM column | Already computed on create; read from ActivityRead |
| NP (Normalized Power) | `Activity.normalized_power` | Already stored from Garmin mapper |
| IF (Intensity Factor) | NP / FTP | Must derive at read time; FTP from AthleteProfile |
| EF (Efficiency Factor) | NP / avg_hr | `advanced_metrics.efficiency_factor()` pure fn exists |
| Work (kJ) | avg_power × duration / 1000 | Derive from `average_power` + `duration_seconds` |
| Elevation | From streams elevation channel | Not yet stored as summary; derive from streams max−min or total ascent |

The `/activities/{id}/streams` endpoint should return both headline derived metrics AND streams arrays. This avoids a second round-trip.

### Anti-Patterns to Avoid

- **Fetching streams on every RecentActivities row render:** Only fetch when SideSheet opens (`enabled: activityId != null`).
- **Storing 1Hz full-resolution streams:** 3600 points × 5 channels = 90KB per activity × hundreds of activities = GB of JSONB. Always downsample to ≤500 points at write time.
- **Blocking activity sync on stream failure:** Streams are enhancement data. The `try/except` wrapper is mandatory.
- **Creating a new `/activities/:id` route:** Phase description explicitly says URL stays at `/dashboard?tab=today`. The SideSheet already enforces this.
- **Using Recharts `ResponsiveContainer` without `min-w-0`:** The existing project rule: any Recharts component inside a flex/grid parent must have `min-w-0` on the wrapper div. uPlot avoids this entirely.
- **Dual-axis Recharts for power+FTP%:** Complex to implement in Recharts 3.x. Use a single-axis normalized chart instead: display power as primary line, FTP as a horizontal reference line at the user's FTP value. OR display IF% (power/FTP × 100) as a single line.

## Common Pitfalls

### Pitfall 1: Garmin `activityDetailMetrics` field mapping uncertainty

**What goes wrong:** The Garmin Connect JSON endpoint `/activity-service/activity/{id}` returns field names like `"directHeartRate"`, `"directPower"`, `"enhancedAltitude"`, `"enhancedSpeed"`, `"directBikeCadence"` — but the exact keys vary by device and activity type. Writing a strict mapper will silently drop streams on some devices.

**Why it happens:** Garmin's unofficial API is not publicly documented; key names are reverse-engineered from browser DevTools observations.

**How to avoid:** Write a flexible mapper that iterates `metricDescriptors`, builds a `key_to_index` dict, and extracts each known key with graceful fallback to `None`. Store `raw_data` in streams dict for debugging. Log which keys were found.

**Warning signs:** All streams are `null` after mapping. Check the raw `activityDetailMetrics` response.

### Pitfall 2: Activity hypertable composite PK blocks naive UPDATE

**What goes wrong:** The `activities` table is a TimescaleDB hypertable with composite PK `(id, started_at)`. SQLAlchemy's `db.execute(update(Activity).where(Activity.id == x))` may miss rows if TimescaleDB chunk pruning applies when `started_at` is not in the WHERE clause.

**Why it happens:** TimescaleDB partitions by `started_at`; without it in the WHERE, the planner may only scan certain chunks.

**How to avoid:** Always include `started_at` in UPDATE WHERE clauses, or fetch the ORM instance first and mutate via `act.sample_streams = streams; await db.flush()` (SQLAlchemy tracks the full PK).

**Warning signs:** `UPDATE activities SET... WHERE id = X` returns 0 rows affected even though the activity exists.

### Pitfall 3: Stream fetch timeout during initial 90-day backfill

**What goes wrong:** 90-day backfill may include 100+ cycling/running activities. Each stream fetch adds ~1s = 100+ additional seconds on top of existing sync time.

**Why it happens:** Stream fetch was added to the per-activity sync loop without considering total time.

**How to avoid:** Add `STREAM_FETCH_ENABLED = True` flag. On initial backfill, optionally skip streams (set a dedicated backfill endpoint or background job). On incremental sync, only fetch streams for newly inserted activities (check count per chunk).

**Warning signs:** Garmin sync times out or hits the existing rate-limit protection.

### Pitfall 4: uPlot initialization in a portal (SideSheet)

**What goes wrong:** uPlot calls `el.clientWidth` during `init(opts, data, el)`. If the SideSheet is mid-animation (x: 100% → 0), `clientWidth` can be 0 and the chart renders at zero width.

**Why it happens:** Same issue as Recharts `ResponsiveContainer` in hidden containers.

**How to avoid:** Init uPlot inside a `useEffect` that fires only after the SideSheet animation completes. Check `el.clientWidth > 0` before init, or defer with `requestAnimationFrame`. Use `ResizeObserver` to trigger resize after the transition (already the pattern in `IntradayModal.tsx`).

**Warning signs:** Chart renders as a thin line or doesn't appear.

### Pitfall 5: `duration_seconds` is nullable on ActivityCreate

**What goes wrong:** `ActivityCreate.duration_seconds` has `Field(..., gt=0)` validation but `Activity.duration_seconds` is `Mapped[int | None]`. When deriving work (kJ) or stride-based downsampling, a null duration causes ZeroDivisionError.

**Why it happens:** The ORM schema allows null; TSS computation already handles this with early None returns.

**How to avoid:** All metric derivation functions must guard `if not duration_seconds: return None`. Streams mapper similarly guards `if not duration_seconds: stride = 1`.

### Backend: Stream mapper skeleton

```python
# backend/app/services/garmin_mapper.py addition
def map_activity_streams(raw_detail: dict, duration_seconds: int | None) -> dict | None:
    """Extract time-series streams from Garmin activityDetailMetrics response.

    Returns None if streams are absent or too short to be useful.
    """
    descriptors = raw_detail.get("metricDescriptors") or []
    metrics = raw_detail.get("activityDetailMetrics") or []

    if not descriptors or not metrics:
        return None

    # Build index → field name map
    idx_to_key: dict[int, str] = {}
    for d in descriptors:
        idx = d.get("metricsIndex")
        key = d.get("key", "")
        if idx is not None:
            idx_to_key[idx] = key

    # Known Garmin field key patterns (LOW confidence — runtime-validated)
    HR_KEYS = {"directHeartRate", "heartRate", "heart_rate"}
    POWER_KEYS = {"directPower", "power", "watts"}
    ALT_KEYS = {"enhancedAltitude", "altitude", "elevation"}
    SPEED_KEYS = {"enhancedSpeed", "speed"}
    CADENCE_KEYS = {"directBikeCadence", "cadence", "bikeCadence", "runCadence"}

    def extract(target_keys: set) -> list[float | None] | None:
        for idx, k in idx_to_key.items():
            if k in target_keys:
                return [m.get("metrics", [None] * (idx + 1))[idx]
                        if isinstance(m.get("metrics"), list) and len(m.get("metrics", [])) > idx
                        else None
                        for m in metrics]
        return None

    hr = extract(HR_KEYS)
    power = extract(POWER_KEYS)
    elevation = extract(ALT_KEYS)
    speed = extract(SPEED_KEYS)
    cadence = extract(CADENCE_KEYS)

    if not hr and not power:
        return None  # No useful streams

    n = len(metrics)
    if n < 10:
        return None

    # Downsample to ≤500 points (uniform stride)
    stride = max(1, n // 500)
    indices = range(0, n, stride)

    def sample(arr: list | None) -> list:
        if arr is None:
            return [None] * len(list(indices))
        return [arr[i] if i < len(arr) else None for i in indices]

    # Build elapsed-time array assuming uniform 1s sampling
    # (Garmin returns one sample per second for most devices)
    t = [i * stride for i in range(len(list(indices)))]

    return {
        "sampled_at": datetime.now(timezone.utc).isoformat(),
        "source": "garmin_connectapi",
        "points": len(t),
        "t": t,
        "hr": sample(hr),
        "power": sample(power),
        "elevation": sample(elevation),
        "speed": sample(speed),
        "cadence": sample(cadence),
    }
```

@router.get(

async def get_activity_streams(
    activity_id: int,
    current_user: Annotated[User, Depends(get_current_active_user)],
    db: Annotated[AsyncSession, Depends(get_db_for_user)],

    activity = await activity_service.get_activity(db, current_user.id, activity_id)

    streams = activity.sample_streams  # None if not yet fetched
    ftp = None
    # Derive additional headline metrics
    from app.services.advanced_metrics import efficiency_factor
    ef = efficiency_factor(activity.normalized_power, activity.average_hr)
    if_val = None
    profile = await get_or_create_profile(db, current_user.id)
    if activity.normalized_power and profile.ftp_watts:
        if_val = round(activity.normalized_power / profile.ftp_watts, 3)

        "has_streams": streams is not None,

            "efficiency_factor": ef,

### Frontend: uPlot stream chart (following IntradayModal pattern)

```typescript
// Source: codebase — frontend/src/components/dashboard/IntradayModal.tsx (pattern)
function StreamChart({ t, values, label, unit, color, height = 180 }: {
  t: number[]
  values: Array<number | null>
  label: string
  unit: string
  color: string
  height?: number
}) {
  const containerRef = useRef<HTMLDivElement>(null)

  useEffect(() => {
    const el = containerRef.current
    if (!el || t.length === 0) return
    // Guard: SideSheet animation may not have completed — defer one frame
    const id = requestAnimationFrame(() => {
      if (!containerRef.current) return
      const opts: uPlot.Options = {
        width: el.clientWidth || 560,
        height,
        series: [
          {},
          { label, stroke: color, width: 1.5, fill: color + '18',
            spanGaps: false, points: { show: false } },
        ],
        axes: [
          { stroke: '#757465', grid: { stroke: '#e2d8c0', width: 0.5, dash: [2,3] },
            ticks: { show: false }, size: 32,
            values: (_u, splits) => splits.map(s => `${Math.floor(s/60)}m`) },
          { stroke: '#757465', grid: { stroke: '#e2d8c0', width: 0.5, dash: [2,3] },
            ticks: { show: false }, size: 40 },
        ],
        legend: { show: false },
        cursor: { drag: { x: false }, x: true, y: false },
      }
      const plot = new uPlot(opts, [t, values], el)
      const ro = new ResizeObserver(() => {
        if (el) plot.setSize({ width: el.clientWidth, height })
      })
      ro.observe(el)
      return () => { ro.disconnect(); plot.destroy() }
    })
    return () => cancelAnimationFrame(id)
  }, [t, values, color, height, label])

  return <div ref={containerRef} className="w-full min-w-0" />
}
```

## Open Questions

1. **Garmin `activityDetailMetrics` exact shape**
   - What we know: `/activity-service/activity/{id}` returns this field per community reverse-engineering; the processor in garmin-health-data uses a different (FIT-based) approach that confirms the time-series data exists in Garmin's system.
   - What's unclear: Exact JSON structure of `metricDescriptors` and `activityDetailMetrics`. Key names for HR/power/elevation vary by device.
   - Recommendation: Log the raw response on first stream fetch in development. The mapper in the implementation plan should log `list(idx_to_key.values())` to surface actual keys. Add a `raw_streams_debug` field in non-production to capture this.

2. **Backfill strategy for existing 90-day activities**
   - What we know: 90-day backfill on first Garmin connect inserts up to ~200 activities. Stream fetch adds ~1s each.
   - What's unclear: Whether to backfill streams synchronously (3+ minutes) or async.
   - Recommendation: Skip stream fetch during initial backfill loop; add a separate `POST /activities/backfill-streams` admin/debug endpoint (or just rely on incremental sync catching future activities).

3. **Elevation: raw metres vs. total ascent**
   - What we know: The streams endpoint returns raw altitude per sample; elevation gain requires computing cumulative ascent from deltas.
   - What's unclear: Whether the elevation channel from Garmin includes barometric corrections or is raw GPS altitude.
   - Recommendation: Display raw elevation profile (chart shows terrain shape) and label clearly as "Elevation (m)". Total ascent can be derived as `sum(max(0, e[i+1]-e[i]) for i)` but don't surface it until verified against Garmin Connect's own ascent values.

4. **Incline chart**
   - What we know: Phase description asks for "elevation/incline" chart. Incline = derivative of elevation / distance.
   - What's unclear: Whether distance stream is returned in the Garmin detail endpoint.
